# -Software Requirements Specification (SRS): Recycling Assistant Bot
1. Introduction
 1.1 Назначение

Настоящий документ определяет спецификацию требований к программному обеспечению Recycling Assistant Bot — Telegram-боту для поиска ближайших пунктов приёма вторичного сырья и получения информации о правильной утилизации различных видов отходов.

Основное назначение системы — предоставить пользователю простой интерфейс для поиска пунктов приёма вторсырья по типу отходов и местоположению пользователя через Telegram.

Бот должен позволять пользователю:

выбрать или указать тип отходов;
определить своё местоположение;
найти ближайшие подходящие пункты приёма;
получить информацию об адресе и режиме работы пункта;
узнать, какие виды вторсырья принимает конкретный пункт;
получить ссылку на маршрут до выбранного пункта;
сохранять интересующие пункты в избранное;
просматривать историю своих запросов.
 
  1.2 Границы системы

В границы системы входят:

пользовательский интерфейс взаимодействия через Telegram Bot API;
модуль обработки сообщений и команд пользователя;
модуль определения категории отходов;
модуль определения местоположения пользователя;
модуль поиска пунктов приёма вторсырья;
модуль фильтрации пунктов по типу отходов;
модуль расчёта расстояния до пунктов;
модуль работы с базой данных;
модуль формирования маршрута;
модуль хранения пользовательских настроек и избранных пунктов;
модуль уведомлений.

В границы системы не входит:

непосредственный приём или транспортировка вторсырья;
организация работы пунктов приёма;
контроль фактического наличия свободных мест для сдачи отходов;
самостоятельное подтверждение достоверности информации, предоставленной сторонними организациями;
переработка отходов;
организация коммерческих операций между пользователем и пунктом приёма.

2. Overall Description

  2.1 Перспектива продукта

Recycling Assistant Bot является автономным программным сервисом, работающим в среде Telegram.

Бот выступает промежуточным звеном между пользователем, Telegram Bot API, базой данных пунктов приёма и внешним картографическим/географическим сервисом.

Общая схема взаимодействия:

Пользователь
     ↓
Telegram
     ↓
Recycling Assistant Bot
     ↓
  Обработка запроса  
     ↓
  Определение категории отхода  
     ↓
  Определение местоположения    
     ↓
  Поиск и фильтрация пунктов    
     ↓
База данных + картографический API
     ↓
Информация о пунктах
     ↓
Пользователь


  2.2 Основные функции

Бот должен обеспечивать следующие основные функции:

обработку команды /start;
отображение главного меню;
обработку команды /help;
выбор категории отходов;
поиск пункта приёма по типу отходов;
получение геолокации пользователя;
поиск ближайших пунктов;
сортировку найденных пунктов по расстоянию;
отображение адреса пункта;
отображение режима работы;
отображение списка принимаемых материалов;
предоставление маршрута до выбранного пункта;
сохранение пункта в избранное;
просмотр истории запросов;
удаление пунктов из избранного;
обработку некорректных запросов;
отправку уведомлений пользователю.
  2.3 Характеристики пользователей

Целевой аудиторией являются пользователи Telegram, заинтересованные в раздельном сборе и правильной утилизации отходов.

Для использования системы не требуется специальных технических знаний.

Пользователь должен уметь:

пользоваться Telegram;
отправлять текстовые сообщения;
нажимать интерактивные кнопки;
при необходимости предоставлять геолокацию.

Предусматривается один основной тип пользователя — обычный пользователь.

В дальнейшем может быть реализована отдельная роль администратора для управления базой пунктов приёма.

  2.4 Ограничения
  
Для работы системы требуется подключение пользователя к Интернету.
Для функционирования бота требуется постоянное подключение серверной части к Интернету.
Определение ближайших пунктов зависит от доступности географических данных.
Актуальность информации о пунктах зависит от источника данных.
Пользователь самостоятельно принимает решение о передаче своей геолокации боту.
Бот не гарантирует фактическую работу конкретного пункта, если информация о его режиме работы не обновлялась в источнике данных.
  
  2.5 Допущения и зависимости

Предполагается, что:

пользователь имеет установленный Telegram;
Telegram Bot API доступен;
сервер имеет постоянное подключение к Интернету;
база данных пунктов приёма доступна приложению;
используемый картографический API доступен;
данные о пунктах приёма имеют координаты или адреса;
для получения расстояния возможно использование координат пользователя и пункта.

3. Specific Requirements

 3.1 Внешние интерфейсы
  
  3.1.1 Пользовательский интерфейс

Взаимодействие пользователя с системой осуществляется через Telegram.

После запуска команды /start бот должен отображать главное меню:

♻️ Recycling Assistant

Что вы хотите сделать?

[🔎 Найти пункт]
[♻️ Выбрать отход]
[📍 Найти рядом]
[⭐ Избранное]
[📜 История]
[ℹ️ Помощь]

При выборе категории отходов пользователь получает список:

Что вы хотите сдать?

[📄 Бумага]
[🧴 Пластик]
[🍾 Стекло]
[🥫 Металл]
[🔋 Батарейки]
[💻 Электроника]
[👕 Одежда]
[Другое]

После выбора категории бот должен запросить местоположение:

📍 Отправьте вашу геолокацию,
чтобы найти ближайшие пункты приёма.

[📍 Отправить геолокацию]

Результат поиска может отображаться следующим образом:

♻️ Найдено 3 пункта:

1. Экоцентр
📍 650 м
🕐 Сегодня: 09:00–20:00
♻️ Принимает: пластик, стекло, металл

[Подробнее]
    3.1.2 Программные интерфейсы

Система должна взаимодействовать со следующими программными компонентами:

Telegram Bot API — приём сообщений, команд, геолокации и отправка ответов пользователю.
Картографический API — получение информации о расположении объектов и построении маршрутов.
База данных — хранение информации о пользователях, пунктах приёма, категориях отходов и пользовательских настройках.
Географический сервис — получение и обработка координат и адресов.

Конкретный набор внешних API определяется на этапе проектирования.


    3.1.3 Аппаратные интерфейсы

Для серверной части требуется:

минимум 1 CPU core;
не менее 512 МБ оперативной памяти;
не менее 1 ГБ свободного дискового пространства;
постоянное подключение к сети Интернет.

  3.2 Функциональные требования

FR-01 — Обработка команд

Бот должен обрабатывать команды /start и /help.

При использовании /start бот должен отображать приветственное сообщение и главное меню.

Метод проверки: демонстрация.

FR-02 — Выбор категории отходов

Бот должен предоставлять пользователю возможность выбрать категорию отходов из доступного списка.

Метод проверки: испытание.

FR-03 — Получение геолокации

Бот должен принимать геолокацию пользователя через Telegram.

При отсутствии геолокации бот должен предоставить альтернативную возможность указать адрес или населённый пункт, если такая функция реализована в выбранной версии системы.

Метод проверки: испытание.

FR-04 — Поиск пунктов

После получения категории отходов и местоположения бот должен выполнять поиск подходящих пунктов приёма.

Результат должен содержать только пункты, соответствующие выбранной категории отходов.

Метод проверки: испытание.

FR-05 — Сортировка по расстоянию

Бот должен рассчитывать расстояние от местоположения пользователя до найденных пунктов и сортировать результаты по расстоянию.

Метод проверки: испытание.

FR-06 — Отображение информации о пункте

Для каждого найденного пункта бот должен предоставлять:

название;
адрес;
расстояние;
режим работы, если информация доступна;
перечень принимаемых материалов;
координаты или ссылку на карту.

Метод проверки: демонстрация.

FR-07 — Получение маршрута

Бот должен предоставлять пользователю возможность открыть маршрут от его текущего местоположения до выбранного пункта.

Метод проверки: демонстрация.

FR-08 — Поиск по текстовому запросу

Бот должен поддерживать текстовые запросы пользователя, например:

«Куда сдать батарейки?»

Система должна определить категорию отхода и предложить соответствующие пункты.

Если автоматическое определение категории невозможно, бот должен предложить пользователю выбрать её вручную.

Метод проверки: испытание.

FR-09 — Избранные пункты

Пользователь должен иметь возможность добавить пункт приёма в избранное.

Бот должен сохранять список избранных пунктов для каждого пользователя.

Метод проверки: испытание.

FR-10 — История поиска

Бот должен сохранять историю поисковых запросов пользователя.

История должна содержать:

категорию отходов;
выбранный пункт;
дату запроса.

Метод проверки: инспекция и испытание.

FR-11 — Уведомления

Бот должен предоставлять возможность создать напоминание, связанное с необходимостью сдачи вторсырья.

Например:

🔔 Напомнить через 30 дней

После наступления указанного времени бот отправляет уведомление пользователю.

Метод проверки: испытание.

FR-12 — Обработка ошибок

При возникновении ошибки бот должен информировать пользователя понятным сообщением.

Например:

⚠️ Не удалось определить ваше местоположение.

Попробуйте отправить геолокацию ещё раз.

или:

⚠️ По вашему запросу не найдено подходящих пунктов.

Метод проверки: испытание.

  3.3 Качество обслуживания (нефункциональные требования)

    3.3.1 Производительность

Ответ на запрос к локальной базе данных должен формироваться не более чем за 2 секунды при штатной нагрузке.
Поиск пунктов через внешний API должен выполняться асинхронно.
Обработка одного пользователя не должна блокировать обработку запросов других пользователей.

    3.3.2 Безопасность

Токен Telegram-бота не должен храниться непосредственно в исходном коде.
Конфиденциальные параметры должны храниться в переменных окружения.
Система не должна сохранять геолокацию пользователя дольше, чем это необходимо для работы соответствующей функции, если пользователь явно не включил функцию, требующую её хранения.
Доступ к административным функциям должен предоставляться только авторизованным администраторам.


    3.3.3 Надёжность и отказоустойчивость

При недоступности внешнего API бот должен корректно информировать пользователя.
Ошибка обработки одного запроса не должна приводить к остановке всего бота.
База данных должна сохранять целостность при перезапуске приложения.
При отсутствии подходящих пунктов бот должен возвращать информативное сообщение.

    3.3.4 Доступность

Бот должен функционировать круглосуточно при наличии доступного серверного окружения и внешних сервисов.

Целевой показатель доступности серверной части — не менее 99%.

3.3.5 Удобство использования
Основные функции должны быть доступны через интерактивные кнопки.
Пользователь не должен знать специальные команды для выполнения основных операций.
Ответы должны быть краткими и структурированными.
Ошибки должны объясняться понятным для пользователя языком.
